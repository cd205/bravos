<objective>
Add a test-DB isolation guard so the test suite can never again silently write fake position lots into the production `bravos_trading` database (IMPROVEMENTS.md item 14, IMPLEMENTATION_PLAN.md Session 0b).

Purpose: Twice (June 29, July 7-9) fake lots matching `^(OPN|PAR|FIF|SPN)_[0-9a-f]{6}` leaked into the production `position_lots` table after test runs on the VM (the VM IS production — daemon and dev workspace share the machine, default DB config points at the live DB). 603 rows were purged on 2026-07-09. The fake lots inflated the risk gate's open-position count and would eventually block real trades at MAX_OPEN_POSITIONS=20.

Root cause understood during planning: the DB-writing tests already use `try/finally: db_connection.rollback()`, but `bravos.execution.positions.open_lot` / `partial_close_lot` call `db_conn.commit()` INTERNALLY (positions.py:29, :112). The test's finally-block rollback is therefore too late — the row is already committed. Pure per-test rollback cannot isolate these paths. The real safety net is a guard that refuses to connect to the production DB at all unless explicitly authorized. That is what this plan delivers.

Output: A guarded `db_connection` fixture that aborts the session loudly when pointed at the production DB without opt-in, plus a post-suite regression finalizer that fails the build if any fake lot leaked.
</objective>
