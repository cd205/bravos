<objective>
Close the fill-replay gap (IMPROVEMENTS.md item 16 / IMPLEMENTATION_PLAN.md Session 1b):
fills that occur while the daemon is disconnected (nightly Gateway restart, bravos-pause,
crash windows) or that were placed by a different clientId are never captured — there is no
reqExecutions call anywhere in the codebase.

The fix requests today's executions from IBKR on every (re)connect and pushes them through
the existing idempotent execDetails → _handle_exec_details path.

Two hard sub-problems must be solved, not glossed:
  1. ORDERING PITFALL: execDetails silently drops fills when ibapp._db_conn is unset. In BOTH
     scripts/run_ingestion._connect_ibkr AND connection._refresh_after_connect,
     run_startup_reconciliation runs BEFORE _db_conn is assigned. reqExecutions must therefore
     be issued as a SEPARATE step AFTER _db_conn is set — never from inside reconciliation.
  2. DOUBLE-COUNT BUG: _handle_exec_details INSERTs with ON CONFLICT (exec_id) DO NOTHING but
     then calls open_lot/partial_close_lot UNCONDITIONALLY. On a replay the INSERT no-ops yet
     the lot is dispatched again → duplicate lot on every reconnect. Lot dispatch must be gated
     on the INSERT actually inserting a row.

Purpose: killing and restarting the daemon around a paper fill loses nothing; no lot is ever
double-counted on reconnect.
Output: REQ_ID_EXECUTIONS constant, replay_todays_fills() method wired into all three
post-connect sequences, conditional lot dispatch, and replay-safety tests.
</objective>

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-1b-01 | Tampering | _handle_exec_details lot dispatch | mitigate | Gate open_lot/partial_close_lot on RETURNING id — a replayed (already-recorded) fill is a true no-op, so repeated reconnects cannot inflate position_lots (the core bug this session fixes). |
